T: Tema 1 - Introducción
P: Un sistema distribuido es un sistema en cuyos componentes, localizados en nodos interconectados, coordinan sus acciones mediante:
a) Paso de mensajes o técnicas derivadas
b) Memoria compartida o virtual
c) El uso de un middleware
d) Todas las respuestas son correctas
R: a
E: Definición de Coulouris: los componentes de un SD se comunican y coordinan sus acciones ÚNICAMENTE mediante paso de mensajes. No hay memoria compartida, y el middleware es una herramienta opcional, no parte de la definición.
Fuente: 25/26 P1.
---
P: En un sistema distribuido podemos asumir que:
a) La red es fiable
b) La latencia es cero
c) La topología de la red puede cambiar
d) La red es segura
R: c
E: a), b) y d) son tres de las 8 falacias de la computación distribuida (suposiciones FALSAS). La falacia es "la topología no cambia"; lo que sí se puede asumir es que puede cambiar.
Fuente: 25/26 P1.
---
P: ¿Cuál de las siguientes propiedades constituye una ventaja de la implementación de un sistema distribuido para proporcionar un servicio TIC?
a) Interconexión de recursos (coste, fiabilidad, saturación, etc.)
b) Seguridad de las comunicaciones.
c) Disponibilidad.
d) Software más simple.
R: c
E: Ventajas de un SD: compartición de recursos, coste/rendimiento, escalabilidad, disponibilidad, concurrencia. La interconexión de recursos y la seguridad de las comunicaciones son INCONVENIENTES, y el software es más complejo, nunca más simple.
Fuente: 25/26 P1.

P: Un middleware de comunicaciones, en sistemas distribuidos:
a) Se sitúa entre el sistema operativo y las aplicaciones distribuidas.
b) Es un tipo de protocolo de comunicación.
c) Su única función es la gestión de la seguridad
d) Todas las respuestas son correctas
R: a
E: El middleware es una capa software entre la plataforma (hardware + SO) y las aplicaciones. No es un protocolo (aunque use protocolos) y sus funciones van mucho más allá de la seguridad.
Fuente: 25/26 P1.

P: Señala la afirmación correcta:
a) Si en un sistema comunicándose mediante HTTP, se realiza una petición GET y se usa el DNS para resolver la dirección IP del servidor, se está usando comunicación indirecta.
b) La comunicación indirecta permite reducir la latencia del sistema
c) En la comunicación directa, los procesos no necesitan conocer la identidad de los demás procesos con los que se comunican.
d) La comunicación indirecta normalmente añade latencia al sistema
R: d
E: La comunicación indirecta mete un intermediario (broker, cola…) entre emisor y receptor: desacopla, pero añade un salto más y por tanto latencia. Usar DNS para resolver un nombre no convierte HTTP en comunicación indirecta (el cliente sigue hablando directamente con el servidor). En la comunicación directa los procesos SÍ deben conocerse.

T: Tema 2 - Diseño de protocolos
P: Si en el contexto de diseño de protocolos hablamos del significado de cada uno de los campos que forman un mensaje, ¿a qué concepto nos estamos refiriendo?
a) Sintaxis
b) Sincronización
c) Semántica
d) Temporización
R: c
E: Sintaxis = estructura/formato de los mensajes (campos, tipos, tamaños). Semántica = SIGNIFICADO de los campos y valores. Sincronización (o temporización) = orden y patrones de intercambio de mensajes.
Fuente: 25/26 P1.

P: Te encuentras diseñando un protocolo, del cual debes seleccionar un formato de serialización de datos para los mensajes. Considerando que el protocolo está destinado a dispositivos de bajos recursos, y que el rendimiento es un aspecto muy importante, ¿cuál de los siguientes sería el formato más apropiado?
a) Protocol Buffers
b) JSON
c) XML
d) Todas las anteriores son adecuadas
R: a
E: Protocol Buffers es binario y compacto: mensajes más pequeños y serialización más rápida. JSON y XML son textuales, más grandes y más costosos de procesar.
Fuente: 25/26 P1.

P: Se está definiendo la sintaxis de un protocolo para el control de un servomotor. El protocolo cuenta con 5 tipos de mensajes distintos. Uno de estos mensajes permite controlar la rotación del servomotor. Este mensaje estará formado por un identificador, que indicará la operación a realizar, y un campo de payload, que será un valor en el rango [-1024, 1024], indicando el grado de rotación con el valor numérico y la dirección con el signo. ¿Cuál debería ser el tamaño en bytes de este mensaje?
a) 2
b) 3
c) 4
d) 5
e) 6
R: b
E: Identificador: 5 tipos de mensaje caben en 1 byte. Payload: [-1024, 1024] son 2049 valores → necesitan 12 bits → 2 bytes. Total 1 + 2 = 3 bytes. Error típico: olvidar el byte del identificador (2) o pensar que 2049 valores caben en 11 bits.
Fuente: 25/26 P1.

P: Se quiere diseñar un protocolo para la comunicación del estado de un conjunto de motores a un sistema SCADA. Sabiendo que los motores cuentan con un sensor de temperatura y un acelerómetro para el control de vibración, indica cuál de los siguientes parece el formato de mensaje más adecuado.
a) ID MENSAJE (1 B) | ID TEMP SENSOR (1 B) | TEMP (1 B) | ID ACC SENSOR (1 B) | ACC (1 B)
b) ID MENSAJE (1 B) | TEMP (2 B) | ACC (2 B)
c) ID MENSAJE (1 B) | ID MOTOR (1 B) | TEMP (1 B) | ACC (1 B)
d) ID MENSAJE (1 B) | SERVER IP (2 B) | SERVER PORT (1 B) | TEMP (1 B) | ACC (1 B)
R: c
E: Hay VARIOS motores, así que hace falta saber de qué motor viene el dato (ID MOTOR); b) no lo tiene. Los ids de sensor de a) son redundantes (cada motor tiene un único sensor de cada tipo) y la IP/puerto de d) son cosa de las capas de red/transporte, no del mensaje de aplicación.
Fuente: 25/26 P1 (bloque A).

P: A la hora de crear un protocolo, señala cuál de los siguientes aspectos hay que considerar:
a) Los lenguajes de programación que van a usarse.
b) El sistema operativo de los nodos que se comunican.
c) La velocidad a la que se procesarán los mensajes.
d) La extensibilidad de las soluciones.
R: d
E: Un protocolo debe ser independiente del lenguaje y del SO de cada extremo (eso es lo que permite la interoperabilidad). Entre las consideraciones de diseño no funcionales, la extensibilidad (poder añadir mensajes/campos en versiones futuras) es la respuesta típica.

T: Tema 3 - Invocación remota
P: ¿Cuál de las siguientes operaciones NO es idempotente?
a) Consultar el saldo de una cuenta bancaria.
b) Asignar un valor fijo a una variable (x = 5).
c) Incrementar el valor de un contador (x = x + 1).
d) Obtener la hora actual del servidor.
R: c
E: Idempotente = ejecutarla N veces deja el estado del servidor igual que ejecutarla una. x = x + 1 cambia el estado en cada ejecución. Consultar, asignar un valor fijo u obtener la hora son idempotentes (que la hora devuelta cambie da igual: no cambia el estado).
Fuente: 25/26 P1.
---
P: En una arquitectura RPC/RMI, ¿cuál es una función del stub del servidor?
a) Serializar los argumentos de la llamada remota.
b) Deserializar la petición y delegar la ejecución al objeto servidor.
c) Gestionar el registro de servicios en el portmapper.
d) Implementar la lógica de negocio de la aplicación.
R: b
E: El stub (o skeleton) del servidor deserializa los argumentos de la petición, invoca al método del sirviente y serializa la respuesta. Serializar los argumentos de la llamada es cosa del stub del CLIENTE; la lógica de negocio la implementa el programador en el sirviente.
Fuente: 25/26 P1.
---
P: El proceso de marshalling en RPC consiste en:
a) Convertir datos complejos del programa a un formato transmisible por red.
b) Establecer la conexión entre cliente y servidor.
c) Localizar el servicio remoto en el registro.
d) Ejecutar el procedimiento remoto en el servidor.
R: a
E: Marshalling = serialización: convertir las estructuras de datos del programa en una secuencia de bytes para enviarla por la red (unmarshalling es lo inverso). Localizar el servicio es tarea del binder.
Fuente: 25/26 P1.
---
P: ¿Cuál es la función principal del binder (registry) en RMI?
a) Ejecutar los métodos remotos solicitados por los clientes.
b) Permitir que los clientes localicen referencias a objetos remotos.
c) Realizar el marshalling y unmarshalling de datos.
d) Gestionar la seguridad y autenticación de las invocaciones.
R: b
E: El binder es un servicio de nombres: el servidor registra sus objetos con un nombre y el cliente obtiene a partir del nombre la referencia remota. Da transparencia de localización. El marshalling lo hacen los stubs.
Fuente: 25/26 P1.
---
P: La principal ventaja de la invocación asíncrona es:
a) El cliente no queda bloqueado esperando la respuesta del servidor.
b) Se garantiza que la operación se ejecutará exactamente una vez.
c) Reducen el número de bytes transmitidos por la red.
d) Simplifican la implementación del middleware.
R: a
E: En la invocación asíncrona el cliente lanza la petición y sigue trabajando; recoge el resultado más tarde (polling o callback). No cambia la semántica de invocación ni el tamaño de los mensajes.
Fuente: 25/26 P1.

T: Tema 1 - Introducción
P: ¿Por qué la ausencia de reloj global es una característica fundamental de los sistemas distribuidos?
a) Permite una mayor seguridad en las comunicaciones.
b) Facilita la programación de aplicaciones distribuidas.
c) Es crítica en el diseño e implementación de cualquier algoritmo distribuido.
d) Reduce la complejidad del diseño e implementación de algoritmos.
R: c
E: Sin un reloj común, los nodos no pueden ponerse de acuerdo en el orden de los eventos solo con sus marcas de tiempo; hay que coordinarse mediante mensajes (relojes lógicos, etc.). Eso complica, no simplifica, cualquier algoritmo distribuido.
Fuente: 25/26 P1R.
---
P: ¿Qué entendemos por «middleware de comunicaciones» en el contexto de los sistemas distribuidos?
a) Hardware dedicado a mejorar el rendimiento de las comunicaciones.
b) Conjunto de protocolos de comunicación que permite la interconexión de nodos en una red.
c) Software que proporciona servicios distribuidos facilitando la comunicación entre el usuario y el sistema.
d) Capa intermedia que proporciona servicios a las aplicaciones distribuidas y demanda servicios de la plataforma.
R: d
E: Es la figura de capas de Coulouris: aplicaciones / middleware / plataforma (SO + hardware). El middleware sirve a las APLICACIONES (no al usuario, por eso c es falsa) y usa los servicios de la plataforma. No es hardware ni un mero conjunto de protocolos.
Fuente: 25/26 P1R.

b) La capacidad de compartir recursos.
c) La provisión de recursos y/o servicios bajo demanda.
d) El empleo de mecanismos de seguridad avanzados.
R: c
E: Lo característico del cloud es la provisión elástica de recursos bajo demanda (IaaS, PaaS, SaaS). Compartir recursos o usar protocolos estándar lo hace cualquier SD.

P: ¿Cuál es la diferencia principal entre «servicio» y «servidor»?
a) Un servicio es un componente de hardware, mientras que un servidor es un componente de software.
b) Un servicio describe una funcionalidad, un servidor es el componente que la implementa.
c) Un servicio es un protocolo de comunicación, mientras que un servidor es una aplicación cliente.
d) Servicio y servidor son términos intercambiables.
R: b
E: Servicio: funcionalidad sobre un conjunto de recursos accesible mediante una interfaz (operaciones bien definidas). Servidor: el proceso en ejecución que implementa uno o varios servicios.
Fuente: 25/26 P1R.

P: ¿Qué es la transparencia de fallo?
a) La capacidad del sistema para ocultar la severidad de los fallos.
b) La habilidad del sistema para detectar y reportar fallos a los usuarios.
c) La capacidad del sistema para continuar operando en presencia de fallos sin que lleguen a ser advertidos.
d) La habilidad del sistema para prevenir todos los tipos de fallos.
R: c
E: Toda transparencia consiste en OCULTAR algo. La de fallos oculta los fallos: el sistema sigue funcionando y el usuario no se entera. Detectar y reportar es justo lo contrario de ocultar.

b) JSON
c) Protocol Buffers
d) YAML
R: c
E: Protocol Buffers es un formato binario: no incluye nombres de campo ni marcas textuales, solo números de campo y valores codificados de forma compacta. XML, JSON y YAML son textuales.

b) La semántica
c) La sincronización
d) El marshalling
R: c

b) Reduce significativamente el tamaño del mensaje y el tiempo de serialización/deserialización.
c) Aumenta el tamaño del mensaje para asegurar la integridad y extensibilidad, pero lo procesa más rápido.

P: ¿Cuántas veces se realiza la serialización en un intercambio de mensajes de tipo RRA (request-reply-ack)?
a) 2
b) 3
c) 4
d) 6
R: b
E: Cada mensaje enviado se serializa una vez: la petición (request), la respuesta (reply) y el ack. Tres mensajes = tres serializaciones.

T: Tema 3 - Invocación remota
P: Se requiere operar remotamente el mecanismo de apertura de una puerta automática. ¿Qué semántica de invocación permitiría conseguir el comportamiento deseado al mínimo coste (memoria, procesamiento y uso de red)?
a) maybe
b) at least once.
c) at most once.
d) exactly once
R: b
E: Abrir una puerta es idempotente: si ya está abierta, volver a abrirla no cambia nada. Por eso se puede reintentar sin filtro de duplicados ni historial (at-least-once). maybe no basta porque podría no abrirse nunca; at-most-once y exactly-once son más caras.
Fuente: 25/26 P1R.

P: En RPC, ¿quién tiene la función de empaquetar los parámetros y construir el mensaje de petición que se envía al servidor?
a) El stub del servidor generado automáticamente a partir de la interfaz.
b) El stub del cliente generado automáticamente a partir de la interfaz.
c) La capa de sockets del sistema operativo en el cliente.
d) El programador, antes de enviarlo mediante la interfaz socket.
R: b
E: El stub (proxy) del cliente, generado por el compilador de interfaces a partir del IDL, serializa el identificador de la operación y los argumentos y envía la petición. El programador solo llama al método como si fuera local.
Fuente: 25/26 P1R.

P: ¿Cuál de las siguientes afirmaciones es FALSA en relación a los sirvientes en un middleware RMI como ZeroC Ice?
a) Varios objetos remotos pueden estar asociados a una única instancia del sirviente.
b) Es posible crear instancias de los sirvientes en cualquier momento de la vida de un servidor RMI.
c) Una misma clase sirviente puede implementar varias interfaces remotas (especificadas en Slice) a la vez.
d) Todos los métodos de un sirviente deben ser métodos invocables remotamente.

E: Un sirviente es un objeto normal del lenguaje: puede tener métodos auxiliares que no estén en la interfaz Slice (y que por tanto no son invocables remotamente). Las otras tres son ciertas (p. ej., un sirviente puede registrarse con varias identidades en el adaptador).

P: ¿Cuál de los siguientes fue un aspecto clave en el diseño del modelo de programación de RPC?
a) El retardo de cualquier llamada RPC debe ser predecible y estar acotado.
b) La RPC debe imitar el modelo de programación de una llamada a procedimiento convencional.
c) El coste computacional debe ser menor o igual al de una llamada a procedimiento convencional.
d) Evitar a toda costa el uso de lenguajes intermedios para definición de la interfaz de servicio remota.
R: b
E: Birrell y Nelson: la RPC debe parecerse lo más posible a una llamada local. Su coste es siempre MAYOR que el de una llamada local, el retardo no se puede acotar en una red asíncrona y se usan IDL para definir las interfaces.

P: Selecciona la afirmación FALSA en lo que respecta a invocación remota:
a) REST es considerado RPC.
b) El servicio Portmapper realiza la vinculación entre cliente y servidor.
c) La semántica Maybe no requiere ni de ACK ni de filtro de duplicados.

a) Los objetos remotos actúan como clientes.
b) Si un proceso invoca un objeto remoto, aunque esté localizado en otro proceso local, se considera llamada remota.
