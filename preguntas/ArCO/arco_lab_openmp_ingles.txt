T: S1 - Basics and fork-join
P: What is OpenMP?
a) A C/C++ and Fortran API for multithreaded shared-memory programming through compiler directives.
b) A message-passing library to split a program across the nodes of a cluster.
c) A compiler option that automatically parallelizes the loops of any sequential program.
d) A C extension to program GPUs through kernels and thread blocks.
R: a
E: OpenMP (Open specifications for MultiProcessing) is an API for C/C++ and Fortran that follows the shared-memory model: you parallelize with directives (#pragma omp ...), library functions and environment variables. Message passing on distributed memory is MPI, not OpenMP.
---
P: Which of these statements about OpenMP is FALSE?
a) OpenMP does not cover automatic parallelization generated by the compiler.
b) The programmer is responsible for using the OpenMP API correctly.
c) OpenMP guarantees that code with directives always gives the right result.
d) OpenMP follows the shared-memory programming model.
R: c
E: OpenMP does not check correctness: if you parallelize a loop with dependencies or leave a race condition, the program will give wrong results. It is the programmer's responsibility.
---
P: What makes OpenMP different from POSIX Threads (Pthreads)?
a) Pthreads uses shared memory and OpenMP uses memory distributed among processes.
b) In OpenMP you just add directives to the sequential code; the runtime decides part of the rest.
c) In OpenMP you have to create, launch and join every thread by hand, just like in Pthreads.
d) OpenMP creates processes instead of threads, so each one has its own memory.
R: b
E: Both are shared-memory models. With Pthreads the programmer explicitly controls every thread (more details to take care of); OpenMP is simpler, because you add directives to the sequential code and the runtime decides part of the behavior.
---
P: What are the three components provided by the OpenMP API?
a) Compiler directives, library functions and environment variables.
b) Compiler directives, system semaphores and messages between processes.
c) Its own compiler, a thread scheduler and a memory manager.
d) Library functions, configuration files and system calls.
R: a
E: One example of each: the directive #pragma omp parallel; the function omp_get_thread_num(); the environment variable OMP_NUM_THREADS=4. In the session all three are used to control the same program.
---
P: What is OMP_NUM_THREADS?
a) A compiler directive.
b) An OpenMP library function.
c) An environment variable.
d) A clause of the parallel directive.
R: c
E: It is set when running, without recompiling: OMP_NUM_THREADS=2 ./hello. Its function equivalent is omp_set_num_threads(n) and its clause equivalent is num_threads(n).
---
P: According to the OpenMP fork-join model, what happens when the end of a #pragma omp parallel block is reached?
a) All the threads in the team keep running the rest of the program in parallel.
b) There is an implicit barrier: all threads are waited for and only the master continues.
c) The first thread to finish continues and the others are cancelled without waiting.
d) Each thread goes on by itself and they all synchronize at the end of main.
R: b
E: The program starts with a single (master) thread. parallel creates a team of threads (fork) that runs the block; at the end there is an implicit barrier (join) and only the master continues.
---
P: How many threads does an OpenMP program start with?
a) As many as the machine has cores.
b) The value of OMP_NUM_THREADS.
c) Just one, the master thread.
d) Two: the master and a worker.
R: c
E: A program always starts with a single thread. The team of threads is only created when a parallel region is reached.
---
P: Which flag must be added to gcc to compile an OpenMP program?
a) -lpthread
b) -fopenmp
c) -O3
d) -openmp-enable
R: b
E: gcc hello.c -o hello -fopenmp. It enables the processing of the #pragma omp directives and links against the OpenMP library (libgomp).
---
P: You compile 01_hello_omp.c (which calls omp_set_num_threads() and omp_get_thread_num()) WITHOUT the -fopenmp flag. What happens?
a) It compiles and runs with 4 threads, because omp.h already includes everything needed.
b) The pragma is ignored and linking fails because the omp_* functions are not defined.
c) The compiler gives a syntax error when it finds the #pragma omp parallel.
d) It compiles with no warnings and runs with a single thread, without any error.
R: b
E: Without -fopenmp the compiler ignores unknown pragmas (with -Wall it warns: "ignoring '#pragma omp parallel'"). Since the OpenMP library is not linked, the calls to omp_set_num_threads, omp_get_thread_num… give "undefined reference" at link time. If the program did not call any omp_* function, it would compile and run sequentially.
---
P: Which header must be included to use the OpenMP functions?
a) <pthread.h>
b) <omp.h>
c) <openmp.h>
d) <parallel.h>
R: b
E: #include <omp.h> declares omp_get_thread_num(), omp_set_num_threads(), omp_get_wtime(), etc.
---
P: What does omp_get_thread_num() return?
a) The number of threads in the current team.
b) The number of processors available on the machine.
c) The identifier of the calling thread within its team.
d) The process identifier (PID) of the program.
R: c
E: It returns the id of the calling thread: 0 for the master, 1..n-1 for the rest of the team.
---
P: What does omp_get_num_threads() return if it is called OUTSIDE any parallel region?
a) The value of OMP_NUM_THREADS.
b) The number of cores of the machine.
c) 1
d) 0
R: c
E: Outside a parallel region only the master thread exists, so the current team has 1 thread. Inside the region it returns the number of threads actually created in that team. To know how many processors there are, use omp_get_num_procs().
---
P: What is omp_get_wtime() used for?
a) To make the current thread sleep for a number of seconds.
b) It returns the wall-clock time in seconds (double), to measure times.
c) It returns the CPU time consumed by the calling thread.
d) It returns the system time as a text string.
R: b
E: It is used like this: double t = omp_get_wtime(); /* region */ printf("%.3f s", omp_get_wtime() - t); In the session it is used to compare the cost of critical, atomic and reduction.
---
P: What does omp_set_num_threads(n) do?
a) It sets the number of threads of the following parallel regions.
b) It creates n threads immediately.
c) It sets the number of threads only of the parallel region where it is called.
d) It limits the number of processors the program can use.
R: a
E: It affects the parallel regions executed afterwards. To set it only for one specific region, use the num_threads(n) clause.
---
P: The number of threads is set in three ways at once: OMP_NUM_THREADS=5, omp_set_num_threads(3) before the region and the num_threads(2) clause on the parallel directive. How many threads will the team have?
a) 5
b) 3
c) 2
d) 10
R: c
E: Precedence (highest to lowest): num_threads clause > omp_set_num_threads() function > OMP_NUM_THREADS variable. Checked: with the three values the team has 2 threads; removing the clause, 3.
---
P: 01_hello_omp.c calls omp_set_num_threads(4) before the #pragma omp parallel. If you run it with !OMP_NUM_THREADS=2 ./hello, how many «Hello world» lines does it print?
a) 2
b) 4
c) 6
d) It depends on the number of cores.
R: b
E: omp_set_num_threads() has priority over the OMP_NUM_THREADS environment variable, so 4 threads are created and each one prints a line.
---
P: You run 01_hello_omp.c (4 threads) five times in a row. What do you observe?
a) The 4 lines always come out in the order 0, 1, 2, 3.
b) The 4 lines come out in a different order depending on the run.
c) The 4 lines always come out in reverse order: 3, 2, 1, 0.
d) Only thread 0 prints, because it is the master thread.
R: b
E: The threads run in parallel and the operating system schedules them non-deterministically, so the order of the lines changes between runs.
---
P: In the lab's Kaggle environment, lscpu shows `CPU(s): 4` and `Thread(s) per core: 2`. What does that mean?
a) 4 physical cores with 1 hardware thread each.
b) 2 physical cores with 2 hardware threads each.
c) 1 physical core with 4 hardware threads.
d) 4 physical cores with 2 hardware threads each.
R: b
E: Physical cores = logical CPUs ÷ threads per core = 4 ÷ 2 = 2 (on a Xeon all cores are identical and Hyper-Threading always gives 2 threads per core). So Kaggle gives 2 physical cores with 2 hardware threads each. Remember it to explain where the speedup stalls in part 2.
---
P: What does omp_get_num_procs() return in the lab's Kaggle environment?
a) 1, because outside a region there is only one thread
b) 2, the number of physical cores
c) 4, the number of logical processors (vCPUs)
d) 8, the cores multiplied by the hardware threads
R: c
E: omp_get_num_procs() returns the available processors, which are the logical ones: Kaggle has 4 vCPUs (2 physical cores × 2 hardware threads). If you do not set the number of threads in any way, OpenMP normally creates as many threads as processors, so a parallel region will have 4.

---
T: S1 - Memory and race conditions
P: In a parallel region, which of these variables is PRIVATE by default?
a) A variable declared before the #pragma omp parallel.
b) A global variable.
c) A variable declared inside the parallel region.
d) A pointer declared in main before the region.
R: c
E: Private: the ones declared inside the region, the ones listed in private(...) and the index of a parallel for. Shared: the ones declared outside the region that are not made private, and the ones listed in shared(...).
---
P: A variable declared BEFORE #pragma omp parallel and not mentioned in any clause is...
a) private
b) shared
c) firstprivate
d) a reduction variable
R: b
E: By default it is shared: there is a single copy for all threads, so concurrent accesses must be synchronized.
---
P: Which variables are private in a #pragma omp parallel for?
a) None: inside a parallel for, every variable is shared by default.
b) The loop index, the body's own variables and those in private(...).
c) Only the variables that appear in a private(...) clause.
d) All the variables that are read or written inside the loop.
R: b
E: The index of a worksharing for loop is automatically private; so are the variables declared inside the region and the ones listed in private.
---
P: In 02_memory_example.c:
```
int product = ...;           // before the region
#pragma omp parallel
{
    int id = omp_get_thread_num();
    product = product * (id + 1);
}
```
How are product and id classified?
a) product private, id shared
b) product shared, id private
c) both shared
d) both private
R: b
E: product is declared outside the region (shared); id is declared inside (private, each thread has its own).
---
P: Why does 02_memory_example.c sometimes give a wrong result?
a) Because omp_get_thread_num() can return the same id to two threads.
b) Because reading, multiplying and writing product is not indivisible: race condition.
c) Because the order of the multiplications changes and that changes the result.
d) Because an explicit barrier is missing at the end of the parallel region.
R: b
E: It is a read-modify-write on a shared variable without synchronization. If two threads read the same value before the other one writes, one of the multiplications is lost.
---
P: In the lab file 02_memory_example.c, product is initialized to 2 and it runs with 4 threads. What is the expected correct result?
a) 24
b) 48
c) 2
d) 96
R: b
E: 2 × 1 × 2 × 3 × 4 = 48. (In the slides the example starts at 1 and the result is 24; in the file it starts at 2.) Since the race is rare with so few operations, you almost always get 48, but the code is still incorrect.
---
P: What is a race condition?
a) A thread finishing its work before the others and being left waiting.
b) Several threads accessing the same data without synchronization, with at least one writing.
c) Having more threads running than cores available on the machine.
d) Two threads running the same function at the same time with different data.
R: b
E: The result becomes non-deterministic: it depends on the execution order. It is fixed by protecting the access (critical, atomic) or by removing the shared access (reduction, private variables).
---
P: race.c launches 4 threads and each one increments counter (shared) 1,000,000 times with counter++ inside a #pragma omp parallel (without for). What value should come out, and what usually comes out with -O0?
a) It should be 1,000,000; it is 1,000,000.
b) It should be 4,000,000; it is usually less.
c) It should be 4,000,000; it is usually more.
d) It should be 1,000,000; it is usually 4,000,000.
R: b
E: With parallel (without for) each thread runs the whole loop: 4 × 1,000,000 = 4,000,000. counter++ is read-add-write without protection, so increments get lost and the result is usually lower (one test gave 1,059,722).
---
P: In race.c the loop is inside #pragma omp parallel, but WITHOUT #pragma omp for. What does that imply?
a) The iterations are automatically split among the 4 threads.
b) Each thread runs all the iterations: the work is repeated.
c) Only the master thread runs the loop and the others wait.
d) The compiler gives an error because the for directive is missing.
R: b
E: parallel only creates the team; to split iterations you need the for worksharing construct (#pragma omp for or parallel for). Without it, each thread runs its own complete loop, which is why 4,000,000 is expected.
---
P: You compile race.c with -O2 instead of -O0 and the result is correct (or almost) much more often. Why?
a) -O2 adds automatic synchronization to shared accesses.
b) The race still exists, but the optimized loop hides it.
c) -O2 turns counter into a private variable of each thread.
d) -O2 makes the whole loop run on a single thread only.
R: b
E: The optimizer turns the loop into a single addition per thread, so there is hardly any window for the race. The code is still incorrect: at -O2 both 3,000,000 and 4,000,000 came out in the tests.
---
P: In race.c (counter = 0 before the region) you add private(counter) to the parallel directive. What does it print at the end?
a) 4,000,000
b) 1,000,000
c) 0
d) A random value, different in each run.
R: c
E: With private each thread works on its own copy (uninitialized), and those copies are discarded when leaving the region. The original variable is not modified, so it is still 0.
---
P: What is the difference between private(x) and firstprivate(x)?
a) None: both create one copy per thread with the value x had outside.
b) private creates uninitialized copies; firstprivate initializes them with the outside value.
c) firstprivate also copies the final value back to the original variable.
d) private creates one copy per thread and firstprivate only one for the first thread.
R: b
E: In both cases the original variable does not change after the region. firstprivate only adds the initialization of each copy with the outside value.
---
P: A variable x is 7 before a parallel region with firstprivate(x). Inside, each thread does x++. What is the value of x after the region?
a) 7
b) 8
c) 7 + number of threads
d) Undefined
R: a
E: Each thread worked with its private copy (7 → 8). The original variable is not touched: it is still 7 after the region (checked).
---
P: What does the shared(list) clause do?
a) It creates a copy of each variable for each thread.
b) There is a single copy of the variables, common to all threads.
c) It combines the threads' copies at the end with an operator.
d) It automatically protects the accesses to those variables.
R: b
E: shared does not synchronize anything: if several threads write to it, it has to be protected.

---
T: S1 - Synchronization
P: Why are synchronization mechanisms needed in OpenMP?
a) Because without them the result can be wrong; in exchange, all synchronization costs time.
b) Because without synchronization the compiler does not accept the OpenMP directives.
c) Because synchronization splits the work better and so speeds up the program.
d) Because they are what creates the team of threads when entering a parallel region.
R: a
E: Parallel programs are non-deterministic. In OpenMP synchronization is achieved with directives, and every mechanism has a cost, so you should choose the cheapest one that solves the problem.
---
P: Which are the HIGH-level synchronization mechanisms of OpenMP seen in the session?
a) critical, atomic and barrier (ordered was not covered)
b) locks and flush, used through library functions
c) POSIX mutexes and semaphores, written as directives
d) parallel, for and sections, which split the work
R: a
E: High level: critical, atomic, barrier and ordered (not covered). Low level: locks and flush (not covered in the lab).
---
P: What does #pragma omp critical do?
a) It runs the block only on the master thread and the others skip it.
b) Only one thread at a time can run the block; the others wait.
c) All threads wait at that point until all of them have arrived.
d) It makes private all the variables used inside the block.
R: b
E: Syntax: #pragma omp critical [(name)] followed by a structured block. It can protect any block of code, implemented as a lock around it.
---
P: What does #pragma omp atomic do?
a) It makes a single update of a variable indivisible, such as x++ or x = x op expr.
b) It protects a block of code of any size with a lock, just like critical.
c) It makes the statement be run by a single thread and the others skip it.
d) It makes the statement run with SIMD vector instructions in each thread.
R: a
E: It applies to a single update statement. It uses hardware atomic instructions, so its overhead is much lower than critical's.
---
P: Comparing critical and atomic, which one is correct?
a) critical protects any block with a lock; atomic, one update with hardware instructions.
b) atomic protects any block with a lock; critical, one update with hardware instructions.
c) Both can protect any block of code, but atomic can only be used with additions.
d) Both do the same and cost the same; only the name of the directive changes.
R: a
E: Rule from the session: if your problem can be solved with atomic, you must use atomic.
---
P: In 03_critical.c the multiplication product = product * (id + 1) is inside a #pragma omp critical, but the printf with product is outside. What do you observe?
a) The final result is always 24 and each thread prints the products 1, 2, 6 and 24 in order.
b) The final result is always 24, but what each thread prints can vary because the printf is outside.
c) The final result is still wrong sometimes, because critical does not protect reading product.
d) The program deadlocks, because the threads wait for each other inside the critical.
R: b
E: The update is protected, so the final result is correct. But the read in the printf is not: when a thread prints, another one may already have multiplied, and the order of the threads is arbitrary anyway.
---
P: 04_atomic.c (4 threads, product = 1) does:
```
int foo(int a) { return a * a; }
...
#pragma omp atomic
product = product * foo(id + 1);
```
What is the final result?
a) 24
b) 576
c) 30
d) Undetermined
R: b
E: foo(id+1) = (id+1)²: 1, 4, 9, 16. Product: 1·4·9·16 = 576. Only the update of product is atomic; the call to foo() runs in parallel outside the protection (it does not need protection because it does not touch shared data).
---
P: In a statement protected with #pragma omp atomic of the form x = x * f(y), which part is protected?
a) The whole statement, including the call to f(y).
b) Only the update of x; f(y) is computed without protection.
c) Only the call to f(y), which is the expensive part.
d) Nothing, because atomic only accepts x++ and x--.
R: b
E: atomic guarantees that the update of that memory location is indivisible. The expression on the other side is computed beforehand, without protection.
---
P: What does #pragma omp barrier do?
a) Each thread waits at that point until all the threads in the team have arrived.
b) Only one thread can go through at a time; the others wait for their turn.
c) It ends the parallel region and from then on only the master continues.
d) It makes atomic all the operations before the barrier.
R: a
E: It is an explicit barrier: it orders phases (everyone finishes phase 1 before starting phase 2).
---
P: Does a barrier (#pragma omp barrier) fix a race condition in memory accesses?
a) Yes: since everyone waits at the barrier, there are no simultaneous accesses anymore.
b) No: it orders phases, but within a phase the threads still access at the same time.
c) Yes, as long as the barrier is placed right before the shared access.
d) Only if after the barrier the variable is declared private.
R: b
E: It is a warm-up question from session 2. The barrier synchronizes the progress of the threads, not mutual exclusion; for that there are critical, atomic or reduction.
---
P: Where does OpenMP place IMPLICIT barriers?
a) Nowhere: they always have to be added with #pragma omp barrier.
b) At the end of parallel and of for, sections and single (unless nowait is used).
c) After every statement that modifies a shared variable.
d) Only at the end of parallel; for, sections and single have none.
R: b
E: The one at the end of a parallel region cannot be removed; the one of the worksharing constructs (for, sections, single) is removed with the nowait clause.
---
P: Each thread prints "phase 1" and then "phase 2". What changes if you put #pragma omp barrier between both printf?
a) Nothing: the lines come out as mixed with the barrier as without it.
b) With the barrier, all the "phase 1" lines come out before any "phase 2".
c) With the barrier only the master thread prints, since it goes through first.
d) With the barrier the program deadlocks, because no thread can go through first.
R: b
E: Without a barrier each thread goes at its own pace and can print "phase 2" while others are still in phase 1.
---
P: race.c is fixed in two ways: protecting counter++ with critical and with atomic. Which one is faster?
a) critical
b) atomic
c) They take exactly the same time.
d) Neither works.
R: b
E: atomic uses a hardware atomic instruction; critical acquires and releases a lock in each of the 4,000,000 increments. Both give the correct result.
---
P: A program has two #pragma omp critical blocks WITHOUT a name, in different functions and protecting different variables. If a thread is inside the first one, can another thread enter the second one at the same time?
a) Yes: each critical block has its own lock even if it has no name.
b) No: all unnamed critical sections share the same global lock.
c) Yes, because they are in different functions and each function has its own lock.
d) It does not compile: there cannot be two unnamed critical blocks in the same program.
R: b
E: Unnamed critical sections use a single global lock, even if they are in different places of the code. If they protect unrelated variables, they slow each other down for no reason. With critical(a) and critical(b) each one has its own lock.
---
P: Can you put nowait on #pragma omp parallel so that the master thread does not wait for the rest at the end of the region?
a) Yes: it removes the barrier at the end of the region and the master goes on without waiting.
b) No: nowait only works on for, sections and single; parallel always waits at the end.
c) Yes, but only if the region also has the num_threads clause.
d) There is no need: parallel has no barrier at the end, so the master never waits.
R: b
E: nowait removes the implicit barrier of the worksharing constructs. The one at the end of the parallel region is the join of the fork-join model and is always there.

---
T: S1 - Clauses and reduction
P: What does the reduction(op: list) clause do?
a) Each thread uses a private copy set to the operator's identity, and at the end they are combined.
b) It protects the variable with a lock every time a thread modifies it.
c) Each thread uses a private copy set to the outside value, and at the end they are discarded.
d) It reduces the number of threads in the team so that there are no conflicts.
R: a
E: There is no lock inside the loop: they are only combined at the end. Valid operators: + * - & | ^ && || min max.
---
P: To what value is each thread's private copy initialized in reduction(*:product)?
a) 0
b) 1
c) To the original value of product.
d) Uninitialized.
R: b
E: It is initialized to the identity element of the operator: 1 for *, 0 for +, etc. At the end the copies are combined with the original value.
---
P: 05_reduction.c (4 threads, product = 1) uses #pragma omp parallel reduction(*:product) and each thread does product = product * (id + 1) and prints it. What do the per-thread lines print, and what is the final result?
a) Each thread prints the accumulated product (1, 2, 6, 24) and the final result is 24.
b) Each thread prints its id+1 (1, 2, 3, 4) and the final result is 24.
c) All the lines print 24, the same as the final result.
d) Each thread prints its id+1 (1, 2, 3, 4), but the final result is 1.
R: b
E: Each private copy is 1 × (id+1) = id+1. They are not accumulated products, because threads do not see each other's copies. At the end they are combined: 1·1·2·3·4 = 24 (checked).
---
P: Order critical, atomic and reduction from CHEAPEST to MOST EXPENSIVE to fix race.c.
a) critical < atomic < reduction
b) reduction < atomic < critical
c) atomic < critical < reduction
d) They all cost the same.
R: b
E: reduction does not synchronize in every iteration (it only combines at the end), atomic uses one atomic instruction per increment and critical one lock per increment. Session takeaway: «Can you use reduction? Use it. If not, atomic. critical is the last resort».
---
P: How is race.c fixed with a reduction?
a) Putting #pragma omp reduction(+:counter) right before counter++.
b) Adding reduction(+:counter) to the #pragma omp parallel.
c) Declaring counter inside the parallel region.
d) Adding private(counter) to the #pragma omp parallel.
R: b
E: #pragma omp parallel num_threads(4) reduction(+:counter), removing any pragma on counter++. Each thread adds into its own copy (starting at 0) and at the end the four are added: 4,000,000.
---
P: What does the num_threads(n) clause do?
a) It sets the number of threads of that region only.
b) It sets the number of threads of all the following regions.
c) It limits the number of cores the program can use.
d) It returns how many threads the current team has.
R: a
E: It has the same effect as omp_set_num_threads() but local to the region, and it has priority over omp_set_num_threads() and OMP_NUM_THREADS.
---
P: Which of these operators is NOT valid in an OpenMP reduction clause (C)?
a) +
b) max
c) &&
d) /
R: d
E: Accepted operators: + * - & | ^ && || min max. Division is not associative, so it cannot be used in a reduction.
---
P: Session 1 challenge: add 1..N with N = 100,000,000 into a long long with 4 threads. What is the correct result?
a) 5,000,000,050,000,000
b) 10,000,000,000,000,000
c) 5,000,000,000,000,000
d) 4,000,000,000
R: a
E: N(N+1)/2 = 100,000,000 × 100,000,001 / 2 = 5,000,000,050,000,000. Without synchronization it is wrong; with critical, atomic and reduction it is right, and the reduction version is the fastest.
---
P: Before the region, `int s = 10;`. With 4 threads this runs:
```
#pragma omp parallel reduction(+:s)
{
    s = s + 1;
}
```
What is the value of s at the end?
a) 4
b) 11
c) 14
d) 50
R: c

d) #pragma omp parallel for simd
R: b
E: parallel for splits among threads (cores) and simd vectorizes each thread's part. reduction is needed both among threads and among lanes. It is the optional comparison of lab 4 (no pragma, simd, parallel for and parallel for simd).
